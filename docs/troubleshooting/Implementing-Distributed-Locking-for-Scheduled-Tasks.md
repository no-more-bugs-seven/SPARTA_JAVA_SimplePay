## 🚩 [TroubleShooting] 다중 서버 환경의 스케줄러 동시성 제어

## 1. 배경
정기 구독 결제 시스템 구현 중, `Spring @Scheduled`를 활용해 매분 결제 대상자를 추출하고 **PortOne API**로 자동 결제를 요청하는 스케줄러를 개발했습니다.

---

## 2. 문제 상황 (Problem)
단일 서버에서는 정상 동작하나, 운영 환경에서 **서버를 2대 이상으로 확장(Scale-out)**할 경우 다음과 같은 치명적 결함이 발생할 가능성을 인지했습니다.
* **중복 결제 발생:** 여러 대의 서버가 동일한 시간에 스케줄러를 실행하여 한 명의 고객에게 중복 결제 요청이 전송되는 현상.
* **데이터 부정합:** 동일한 구독 데이터에 대해 여러 서버가 동시에 접근하여 상태를 변경하려는 경합 조건(Race Condition) 발생.

---

## 3. 1차 해결 방안 및 트러블슈팅
다중 서버 간 스케줄러 실행 권한을 제어하기 위해 `ShedLock` 라이브러리를 도입했습니다.

**[초기 이슈]**
* `@SchedulerLock` 적용 후, Lock 정보를 관리할 `shedlock` 테이블이 DB에 존재하지 않아 서버 구동 시 `BadSqlGrammarException` 발생 및 시스템 중단.

**[조치 사항]**
환경별로 락 관리 테이블을 구성하여 서버 간 실행 권한을 제어했습니다.
* **Local (H2):** `schema.sql`을 활용해 서버 구동 시 자동으로 테이블이 생성되도록 스크립트화.
* **Prod (RDS):** 영구적인 락 전용 테이블을 수동 생성하여 인프라 세팅 완료.
* **결과:** 하나의 서버가 락을 획득하면 다른 서버는 작업을 건너뛰도록 설정하여 **중복 결제 문제를 완전히 해결**.

---

## 4. 회고 및 한계점 (Reflections)
DB 기반의 락(`JdbcTemplateLockProvider`)으로 문제를 해결했으나, 운영 과정에서 RDBMS 기반 락의 단점을 파악했습니다.

1. **DB 커넥션 자원 낭비:** 락 획득/해제 과정에서 지속적으로 DB 커넥션을 점유하여, 정작 중요한 비즈니스 로직(결제, 주문)의 성능 저하를 유발할 수 있는 병목 지점 형성.
2. **관리 포인트 증가:** 운영 DB 스키마 변경 권한이 엄격한 환경에서 락 전용 테이블을 유지보수해야 하는 인프라적 제약 발생.

---

## 5. 향후 개선 계획: Redis 기반 분산 락 도입
현재의 DB 부하 문제를 해결하기 위해 **Redis**로 ShedLock 저장소를 마이그레이션할 예정입니다.

* **In-Memory 기반 고성능:** DB 커넥션 풀을 소모하지 않고 빠른 I/O 속도로 락 제어 가능.
* **인프라 분리:** 메인 DB와 락 관리 저장소를 분리하여 비즈니스 로직의 독립성과 시스템 안정성 고도화.
