## 🚩 [TroubleShooting] OAuth2 배포 환경 리다이렉션 이슈 및 사용자 프로필 데이터 정합성 해결

## 1. 배경
로컬 개발 환경(HTTP)에서는 Google OAuth2 로그인이 정상적으로 동작했으나, 
**AWS 배포 환경(HTTPS)** 적용 후 특정 상황에서 로그인이 실패하거나 일부 사용자만 접속이 가능한 불안정한 상태가 발생했습니다.

---

## 2. 문제 상황

#### 1. 프로토콜 불일치 (HTTP vs HTTPS)
* **현상:** 브라우저에서 OAuth2 인증 후 리다이렉트 시 `redirect_uri`가 `http://...`로 전달되는 현상 발생.
* **원인:** 실제 서버는 SSL(HTTPS) 환경이지만, L4/L7 로드밸런서나 리버스 프록시(Nginx 등)를 거치면서 내부 서버로 요청이 전달될 때 프로토콜 정보가 유실되어 Spring Security가 인증 응답 주소를 HTTP로 생성함.

#### 2. Google API Console 설정 제한
* **현상:** 개발자 계정 외에 일부 외부 사용자들의 로그인이 차단됨.
* **원인:** Google Cloud Console의 OAuth 동의 화면 설정이 **'테스트(Testing)'** 모드로 유지되어 있어, 등록된 테스트 사용자 외에는 인증 토큰 발급이 거부됨.

#### 3. 고정된 필드값으로 인한 데이터 중복 (Unique Constraint)
* **현상:** 신규 구글 유저 회원가입 시 `DataIntegrityViolationException` 발생.
* **원인:** Google 프로필에서 제공하지 않는 **전화번호(Phone Number)** 필드에 고정된 더미 값을 할당하여, 두 번째 사용자부터는 DB의 Unique 제약 조건에 걸려 가입이 실패함.

---

## 3. 해결 방안 

**1. Forwarded Headers 전략 적용**
* **조치:** `application.yml` 파일에 `server.forward-headers-strategy: native` 속성을 추가하여 프록시 서버의 헤더를 신뢰하도록 수정.
* **결과:** 클라이언트의 원본 요청 헤더(`X-Forwarded-Proto`)를 Spring이 인식하게 되어, **리다이렉션 시 강제로 HTTPS 프로토콜을 유지**하도록 수정했습니다.

**2. OAuth 동의 화면 '앱 게시'**
* **조치:** Google Cloud Console에서 앱 상태를 '테스트'에서 **'프로덕션(Production)'**으로 변경.
* **결과:** 모든 일반 사용자가 제한 없이 소셜 로그인 서비스를 이용할 수 있도록 **승인 상태를 업데이트**했습니다.

**3. 유저 스키마 및 가입 로직 유연화**
* **조치:** 전화번호 필드의 **Unique 제약 조건을 제거하고 선택 사항(Nullable)으로 변경**하여 소셜 로그인 데이터의 가변성에 대응.
* **결과:** 다양한 소셜 프로필 환경에서도 데이터 충돌 없이 **안정적인 회원가입 프로세스를 확보**했습니다.

---

## 4. 회고 (Retrospect)
* **인프라 이해의 중요성:** HTTPS 배포 환경에서는 프록시 서버와 어플리케이션 간의 **헤더 전달(Forwarding)** 설정이 필수적임을 학습했습니다.
* **데이터 설계의 유연성:** 외부 플랫폼 데이터는 언제든 누락될 수 있음을 가정하고, DB 스키마를 더욱 유연하게 설계해야 함을 체득했습니다.
